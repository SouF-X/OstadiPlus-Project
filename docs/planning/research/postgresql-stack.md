## Identity and OpenIddict

[Microsoft.AspNetCore.Identity.EntityFrameworkCore 10.0.14](https://www.nuget.org/packages/Microsoft.AspNetCore.Identity.EntityFrameworkCore/10.0.14) targets net10.0 and requires EF Relational >=10.0.14. [OpenIddict.EntityFrameworkCore 7.7.2](https://www.nuget.org/packages/OpenIddict.EntityFrameworkCore/7.7.2), released 2026-10-10, includes a net10.0 target requiring EF Relational >=10.0.11. These documented ranges intersect with the Npgsql provider's EF 10 range. OpenIddict's own major does **not** need to equal EF's major.

OpenIddict documents EF stores for applications, authorizations, scopes, and tokens, and an `IdentityDbContext` when combined with ASP.NET Core Identity. Its example uses SQL Server; the PostgreSQL candidate uses the Npgsql EF provider and must generate and review PostgreSQL migrations. This is a composition inferred from those documented integration seams, not a vendor-certified Ostadi Plus stack. [OpenIddict EF integration](https://documentation.openiddict.com/integrations/entity-framework-core), [Identity model and migrations](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/customize-identity-model?view=aspnetcore-10.0).

## Hangfire PostgreSQL storage and fee boundary

Use the separate community **Hangfire.PostgreSql** storage candidate, rather than the SQL Server storage package. [Hangfire.PostgreSql 1.21.1](https://www.nuget.org/packages/Hangfire.PostgreSql/1.21.1), dated 2026-02-11, targets netstandard2.0 and declares Hangfire.Core >=1.8.0, Npgsql >=6.0.11, Dapper >=2.0.123, Dapper.AOT >=1.0.48, and Microsoft.CSharp >=4.7.0. [Hangfire.AspNetCore 1.8.25](https://www.nuget.org/packages/Hangfire.AspNetCore/1.8.25) is a stable hosting-integration candidate. The provider README documents `UsePostgreSqlStorage`/`UseNpgsqlConnection`, drops the old Npgsql5 package, and defaults to preparing its schema. [Provider repository](https://github.com/hangfire-postgres/Hangfire.PostgreSql).

The provider's dependency range admits Npgsql 10 and has no declared upper bound, but its source package reference still starts at Npgsql 6.0.11. **Package-range intersection is insufficient evidence of runtime compatibility across those driver majors**: verify restore, startup, schema preparation, enqueue/execute, recurring jobs, concurrency, and restart/retry behavior against the selected PostgreSQL/driver versions. [Provider project dependencies](https://raw.githubusercontent.com/hangfire-postgres/Hangfire.PostgreSql/master/src/Hangfire.PostgreSql/Hangfire.PostgreSql.csproj). Releases demonstrate ongoing publication, not a contractual maintenance horizon. Hangfire expressly provides no official support or quality/security guarantee for community extensions. [Hangfire extension policy](https://www.hangfire.io/extensions.html).

The fee evidence is compatible with evaluating a zero software-license-fee baseline: [PostgreSQL's license](https://www.postgresql.org/about/licence/) allows use without fee; Npgsql driver/provider metadata lists the PostgreSQL license; EF Core and Identity list MIT; OpenIddict lists Apache-2.0 (linked metadata above). Hangfire Core's free commercial-use offering is LGPLv3 with community support; the PostgreSQL provider also declares LGPLv3. These licenses retain obligations: record them and review the eventual dependency/distribution inventory without inferring that no obligations exist. [Hangfire pricing](https://www.hangfire.io/pricing/), [provider license](https://raw.githubusercontent.com/hangfire-postgres/Hangfire.PostgreSql/master/LICENSE.md).

Paid Hangfire Pro adds batches/Redis storage; paid Ace adds throttling. They are outside the zero-fee candidate, and their official storage-support lists do not include PostgreSQL. Preserve durable jobs and the transactional outbox requirement without assuming those paid features or automatic atomicity between an EF business transaction and a separate Hangfire enqueue. [Pro](https://www.hangfire.io/pro/), [Ace](https://www.hangfire.io/ace/). Hosting, storage, backup operation, and any purchased support are separate costs.

## Gates before implementation or production approval

1. **Restore and integration:** Recheck release dates, security advisories, package licenses and all transitive constraints; pin coherent stable versions. Test Identity/OpenIddict migrations and required authentication flows on real PostgreSQL. Test Hangfire under the selected Npgsql major, with controlled schema/DDL privileges, outages, duplicate delivery, worker termination and recovery. Verify the application's outbox and idempotency behavior; no such test was run here.
2. **RLS roles:** PostgreSQL superusers and `BYPASSRLS` roles always bypass policies; table owners normally bypass them, while `FORCE ROW LEVEL SECURITY` can subject owners to policies. Whole-table operations such as `TRUNCATE` are outside RLS. Design separate migration/owner and runtime roles and prove fail-closed tenant isolation for reads/writes, workers and administrative paths. `FORCE` does not neutralize superuser/BYPASSRLS. [PostgreSQL RLS](https://www.postgresql.org/docs/18/ddl-rowsecurity.html).
3. **Pooled tenant context:** EF context pooling and driver connection pooling are separate. A pooled context reuses instances, `OnConfiguring` runs once, and EF does not generally reset manually manipulated driver state. Npgsql enables connection pooling by default and warns that `No Reset On Close=true` can leak state. Establish authenticated tenant context for each unit of work/transaction, and prove cleanup across reuse, exceptions, retries and workers before enabling context pooling or changing connection-reset behavior. [EF pooling](https://learn.microsoft.com/en-us/ef/core/performance/advanced-performance-topics), [Npgsql pooling parameters](https://www.npgsql.org/doc/connection-string-parameters.html).
4. **Backup/PITR:** PostgreSQL supports base backups plus a continuous WAL archive for point-in-time recovery; logical `pg_dump` output alone cannot supply WAL replay. Verify the chosen host's access, retention, encryption, off-host storage and recovery procedures, then execute restore drills against the required RPO/RTO and job/outbox consistency. No host or recovery configuration is selected or proven. [PostgreSQL PITR](https://www.postgresql.org/docs/18/continuous-archiving.html).
